# Nexpage Codex 可信视觉包设计

日期：2026-07-19

状态：设计已确认，等待用户评审

范围：`--profile codex` 与 `--with-codex`

## 1. 背景

Nexpage 当前可以从目标网站生成精简的 `codex-context/`。用户的真实使用方式不是逐条解释这些文件，而是直接把整个目录交给 Codex，只说明“这是我的目标视觉风格”，然后再单独讨论新产品的用户需求、功能和信息架构。

因此，Codex 包不能只是原始提取结果的精简格式。它必须是一份自解释、可信、可直接用于建立新项目视觉基准的设计上下文。

Greptile 实测暴露了现有实现的主要问题：

- `variables.css` 可能输出 `[object Object]` 等非法 CSS。
- `tokens.json` 可能引用不存在的圆角和阴影 Token。
- 颜色数值正确，但语义角色可能错误。
- 关键的切角按钮形状没有进入结构化规则。
- 动画名称正确，但没有绑定实际长周期。
- 原网站区域识别重复且置信度低，容易干扰新产品的信息架构。
- 单一首屏截图不足以表达完整页面的深浅区块和视觉节奏。

## 2. 目标

用户只需要把 `codex-context/` 交给 Codex，并说明它是目标视觉风格。Codex 读取后应当：

1. 建立来源网站的视觉语言基准。
2. 继承色彩关系、排版层级、形状、材质、组件气质、间距节奏和动效语言。
3. 不复制来源网站的品牌、Logo、文案、专有资产、产品内容和信息架构。
4. 在用户尚未提供产品需求时，不直接复制或生成来源页面，而是等待需求。
5. 在用户提供需求后，先设计新产品的信息架构，再应用已确立的视觉语言。
6. 无需用户额外指出哪些 Token 无效、哪些颜色角色错误或哪些规则应忽略。

## 3. 非目标

第一版不包含：

- Nexpage 运行时接入 Codex、OpenAI API 或其他视觉大模型。
- 自动生成新产品页面。
- 复制来源网站的 HTML、CSS、Logo、插画或品牌内容。
- 多页面爬取。
- 移动端或多断点截图。
- 独立的组件截图目录。
- `quality-report.json` 或 `manifest.json`。
- 修改原有 40 多文件完整导出的格式和用途。

## 4. 用户工作流

```text
目标网站
  ↓
Nexpage 本地提取与验证
  ↓
生成 codex-context/
  ↓
用户将目录交给 Codex，并说明“这是目标视觉风格”
  ↓
Codex 建立视觉基准，但不复制来源页面结构
  ↓
用户再讨论自己的需求、功能和信息架构
  ↓
Codex 将已确立的视觉语言应用到新产品
```

Nexpage 与 Codex 是两个独立阶段。Nexpage 不需要登录 Codex，不需要 API Key，也不消耗大模型 Token。

## 5. 方案选择

采用“可信视觉模型层”，而不是只修格式器或重新打开网页进行第二次完整分析。

```text
原有设计提取
  +
Codex 专用关键视觉证据
  ↓
可信视觉模型
  ├─ verified：允许进入正式 CSS 和 Token
  ├─ candidates：只允许进入 CODEX.md 候选区
  ├─ rejected：内部拒绝并记录原因
  └─ rhythm：只表达抽象视觉节奏
  ↓
统一生成 CODEX.md / tokens.json / variables.css / motion.json
  ↓
包级质量验证
```

四个文本文件必须从同一份可信视觉模型生成，禁止分别解释原始数据而产生矛盾。

## 6. 输出目录契约

```text
codex-context/
├── reference.png
├── reference-full.png
├── CODEX.md
├── tokens.json
├── variables.css
└── motion.json        # 仅在存在可靠动效时生成
```

无可靠动效的网站生成 5 个文件；有可靠动效的网站最多生成 6 个文件。

### 6.1 reference.png

当前桌面视口截图，用于判断首屏字号比例、导航高度、留白和构图。

### 6.2 reference-full.png

完整页面截图，用于判断深浅区块、组件密度、强调色比例和完整视觉节奏。它是辅助证据；截图失败时允许降级生成。

### 6.3 CODEX.md

整个目录的唯一入口和内置使用说明，包含：

- 视觉包用途和禁止复制的边界。
- Codex 读取后的行为规则。
- 文件阅读顺序。
- 证据优先级。
- 已验证视觉语言。
- 低可信候选。
- 抽象视觉节奏。
- 数据限制和安全规则。

### 6.4 tokens.json

只包含已经验证、适合机器读取的数据。禁止出现候选数据、空占位符或断裂引用。

### 6.5 variables.css

只包含可以直接接入项目的合法 CSS 自定义属性。禁止包含非自定义属性、复杂对象字符串和来源站点的运行时 `--tw-*` 噪音。

### 6.6 motion.json

只保存确认存在的动效名称、作用对象、实际周期、缓动、循环方式、类别和 reduced-motion 建议。没有可靠动效时不生成。

## 7. 证据优先级

Codex 包明确使用以下优先级：

```text
用户的新产品需求
  ↓
reference.png / reference-full.png
  ↓
CODEX.md 中的已验证规则
  ↓
variables.css / tokens.json / motion.json
  ↓
CODEX.md 中的低可信候选
```

用户需求决定产品功能和信息架构；来源截图只决定视觉语言。

## 8. Codex 专用证据收集

只有 `--profile codex` 和 `--with-codex` 运行轻量的关键视觉证据收集。它复用当前已经打开的页面，不重新启动浏览器、不重新登录、不重新导航，也不调用 AI。

在页面关闭前读取：

- H1、正文、导航和技术标签的计算字体样式。
- 高意图 CTA 和次要 CTA 的颜色、文字、边框与形状。
- 重复卡片和控件的圆角、边框和 `clip-path`。
- 页面主要表面和背景材质证据。
- 实际运行的动画名称、目标、持续时间、缓动与循环方式。
- 形成页面深浅节奏所需的可见表面证据。

普通完整输出模式不运行这一步。

## 9. 可信视觉模型

### 9.1 verified

满足以下条件之一的数据可以成为已验证规则：

- 来自实际渲染后的计算样式，并在明确视觉角色中重复出现。
- 来自 H1、正文、主 CTA 等关键角色，即使实例数量较少，但用途清晰且无冲突。
- 是被多个独立证据共同支持的稳定值。

只有 `verified` 可以进入 `tokens.json` 和 `variables.css`。

### 9.2 candidates

以下数据只能作为候选：

- 只出现一次且用途不明确。
- 在多个视觉角色之间存在冲突。
- 可能是装饰性、临时状态或第三方组件产生。
- 证据不足以决定语义名称。

候选只进入 `CODEX.md`，并明确要求结合截图判断。

### 9.3 rejected

以下数据直接拒绝：

- `null`、`undefined`、空字符串或非标量复杂对象。
- `[object Object]` 等序列化错误。
- 浏览器默认色或默认样式，且没有来源站点使用证据。
- 指向不存在定义的 Token 引用。
- 无法成为合法 CSS 或 JSON Token 的值。
- 一次性布局测量值被误认为语义间距。

`rejected` 不输出给 Codex。

### 9.4 rhythm

原网站的具体 Hero、Testimonials、FAQ 等区域顺序不作为新产品结构。模型只保留：

- 首屏字号与留白关系。
- 深浅表面交替方式。
- 信息密度变化。
- 强调色面积和出现频率。
- 卡片、边框和背景材质的重复规律。
- 长页面如何通过视觉表面形成节奏。

## 10. 七类视觉信息

### 10.1 颜色角色

根据使用位置判断 `surface`、`ink`、`text`、`action-primary`、`action-secondary`、`accent`、`border` 和 `grid`，不再只按出现次数选择 primary。

### 10.2 字体角色

输出 `display`、`body`、`mono` 和必要的 `ui` 角色，禁止 `font-body-2`、`font-font-2` 等无意义名称。

### 10.3 形状语言

记录可靠的圆角、切角、`clip-path`、边框粗细、按钮轮廓、卡片轮廓和标签形状。没有圆角时不生成圆角占位引用。

### 10.4 背景与材质

记录页面底色、深浅表面、网格、点阵、线条、渐变和纹理密度。只描述插画类型，不复制来源品牌资产。

### 10.5 间距与布局节奏

只保留重复出现且能形成稳定尺度的间距。过滤 233px、337px 等一次性测量结果。记录容器宽度、左右留白和内容密度，但不规定新页面板块顺序。

### 10.6 组件视觉模式

描述主要按钮、次要按钮、卡片、导航和技术标签“长什么样”，不规定新产品必须包含来源网站的业务组件。

### 10.7 动效语言

绑定动画名称、作用对象、真实持续时间、缓动、循环方式和类别。区分微交互与长周期环境动画。

## 11. CODEX.md 行为契约

`CODEX.md` 必须使用明确的指令语言告诉下游 Codex：

1. 本目录用于建立视觉语言，不用于复刻来源页面。
2. 未收到新产品需求时，不直接开始生成页面；先确认视觉基准已读取并等待需求。
3. 同时收到需求时，先设计用户自己的信息架构，再应用视觉语言。
4. 不复制品牌、Logo、文案、专有插画和产品内容。
5. 截图负责视觉比例，已验证规则负责语义，CSS/Token 负责精确数值。
6. 候选不能被视为强制规范。
7. 新产品可用性和用户需求优先于视觉模仿。

## 12. 质量门槛与错误处理

### 12.1 核心成功条件

必须满足：

- `reference.png` 成功生成。
- `CODEX.md` 包含用途、行为规则和证据边界。
- `tokens.json` 可解析，且所有引用都存在。
- `variables.css` 只包含合法自定义属性和值。
- 候选没有进入正式机器文件。
- 文件之间不存在已验证语义冲突。
- 空动效不会产生 `motion.json`。

核心条件失败时，Codex 包生成失败，CLI 必须显示具体原因，不能显示成功。

### 12.2 辅助证据降级

`reference-full.png` 因无限滚动、超长页面、Canvas 或页面限制失败时，允许生成核心包，但必须：

- 在 `CODEX.md` 说明视觉证据只覆盖桌面首屏。
- 在终端提示完整页面视觉覆盖有限。
- 禁止根据缺失证据推断完整页面节奏。

### 12.3 原子写入

Codex 包先写入临时目录并执行完整验证：

```text
临时目录生成
  ↓
验证通过 → 原子改名为 codex-context
验证失败 → 清理临时目录并报告原因
```

失败不能留下看似可用的半成品目录。

如果目标位置已经存在旧的 `codex-context/`，旧目录在新包验证通过前保持不变。替换时先将旧目录改名为同级备份，再切换新目录；切换失败必须恢复旧目录，切换成功后才清理备份。

### 12.4 模式兼容性

- 默认模式：保持原有完整输出，不运行 Codex 专用证据收集。
- `--profile codex`：只生成经过验证的 Codex 包。
- `--with-codex`：完整输出照常生成；Codex 包失败时保留完整输出并单独报告失败。

## 13. 模块边界

采用以下内部职责边界；实施计划可以在不改变职责的前提下调整具体文件名：

```text
src/codex/
├── collect-evidence.js
├── verified-model.js
├── validate-package.js
└── format-context.js
```

- `collect-evidence.js`：只负责从当前 Page 读取关键计算样式和截图证据。
- `verified-model.js`：只负责分类、语义转换和降噪。
- `validate-package.js`：只负责文件级和包级质量检查。
- `format-context.js`：只负责从可信模型生成文本内容。

现有 `codex-context.js` 的职责应拆分或缩减为公共入口与写入编排。

## 14. 自动化测试

至少覆盖：

1. 复杂对象不能生成 `[object Object]`。
2. 空圆角和空阴影不能产生断裂引用。
3. 所有 JSON Token 引用都能解析。
4. CSS 只包含合法自定义属性。
5. 深色文字与绿色 CTA 能映射到不同颜色角色。
6. 字体能映射到 display、body、mono。
7. 可靠 `clip-path` 能进入形状 Token。
8. 动画名称、对象和真实周期能够绑定。
9. 一次性异常间距不会进入正式 scale。
10. 来源区域只能形成视觉节奏，不能成为新页面结构要求。
11. 完整截图失败时正确降级。
12. 核心验证失败时不留下半成品目录。
13. 默认完整输出行为不变。
14. `--profile codex` 只生成 Codex 目录。
15. `--with-codex` 保持完整输出并附加可信包。

## 15. Greptile 回归验收

真实提取必须确认：

- 不存在 `[object Object]`。
- 不存在未定义 radius/shadow 引用。
- `#28e99f` 被识别为主要操作色。
- `#3d3b4f` 被识别为文字墨色和深色表面。
- Anybody、DM Sans、Space Mono 分别映射到 display、body、mono。
- 切角按钮被明确表达为形状规则。
- 动画证据包含 6000ms 和 40000ms 实际周期。
- `CODEX.md` 不要求复制 Greptile 的页面结构。
- 首屏与完整页面截图均成功生成，或完整截图失败时明确降级。

## 16. 最终人工验收

将新生成的 `codex-context/` 交给一个新的 Codex 任务，只说明“这是我的目标视觉风格”。合格表现为：

1. Codex 正确概括来源网站的视觉语言。
2. Codex 明确不会复制品牌和页面结构。
3. 在未收到产品需求时等待需求，不直接生成来源首页。
4. 后续能把视觉语言应用到不同产品的信息架构。

这一步是对输出质量的人工验收，不构成 Nexpage 对 Codex 的运行时依赖。

## 17. 成功标准

第一版成功必须同时满足：

- 用户不需要补充“忽略无效 Token”等纠正提示词。
- Codex 包所有机器文件通过语法和引用检查。
- 关键视觉特征不仅存在于截图，也能被结构化规则表达。
- 低可信推断不会伪装成正式设计规范。
- 来源页面结构不会干扰新产品需求分析。
- 默认完整导出保持兼容。
